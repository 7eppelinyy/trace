### RV01 · P0 · R/S：生产模式、会话签发与小程序客户端相互矛盾

**证据位置：** `.env.example:14`；`trace/common/modes.py`；`trace/api/routers/auth.py:38`；`miniprogram/utils/api.js:68`；`trace/api/app.py`。

新模板写 `TRACE_MODE=real`，而程序只接受 `test/offline/production`，`is_production()` 只有在值为 production 时才返回 true。API 启动路径没有先校验模式，`real` 环境下仍开放任意 user_id 的 dev session 签发。

本次用同一个临时 API app 切换环境：

```json
{
  "production_dev_grant": 403,
  "real_dev_grant": 200,
  "real_issued_subject": "audit-victim",
  "real_is_production": false
}
```

与此同时，小程序固定 `grant_type: 'dev'`，因此真正开启 production 后登录失败。`grant_type='wechat'` 的服务端分支只是创建随机访客用户，没有接收或校验微信 code，不能称为微信登录。改客户端为 guest 也要同步存储服务端 user_id，否则客户端仍发送旧 `X-User-ID`，会与 session subject 冲突。

**影响：** 按部署模板操作可能绕过生产门禁；按正确生产模式操作，小程序又无法正常登录。这是“默认路径没有端到端验证”的直接例子。

**修复要求：**

1. 所有进程启动时验证模式，未知值直接拒绝启动；统一模板与文档为 production。
2. dev grant 只在明确的开发认证开关下启用；默认 offline 也不应意味着对公网开放任意主体签发。
3. 完整接通生产访客或微信认证，准确命名能力；身份 ID 来自服务端响应，缓存按环境/账户隔离。
4. 公共 session 接口加入数量、速率与滥用限制；新设备/过期会话如何恢复同一账户需有明确方案。
5. CORS 列表实际仍含 `*`，且不含新研究更新接口使用的 PATCH；整理为明确配置，不把 CORS 当认证。

**验收：** 使用小程序实际客户端协议测试 production 登录、自选读取、退出/撤销、过期恢复；非法模式启动失败；A 不能签发 B 的会话；不允许通过把生产改成 real/offline 来“解决登录”。

**位置：** `trace/pipeline.py:322,347,352,372`；`trace/db/repositories.py:986`。

新增恢复扫描只选 `pending/blocked_budget`。执行前 job 改为 processing，普通异常/进程退出时留在 processing；可预期 LLM unavailable 被标 failed，也不会再被选中。lease_until 字段存在但分析消费路径没有实际领取/回收租约。

### RV05 · P0 · R/S：关闭提醒后仍可发送，Outbox 与分析停止相互阻塞

**位置：** `trace/alerts/delivery_worker.py`；`trace/pipeline.py:411`；`trace/db/repositories.py:claim_batch/mark_sent/mark_failed`。

worker 只检查 channel_binding 是否有效，没有重查通知偏好、静音、关注撤销等投递时条件。本次先入队，再将全局 enabled=False，伪 sender 仍调用一次并返回 sent。

Outbox 消费在 `_run_once()` 后半段；Stage A/B 的预算 STOP、缺 key 等提前返回都会跳过消费。因此“无新新闻也能消费”虽然改善了一个场景，但“分析停止不影响已排队通知”没有实现。

其他代码确认风险：

- 一次领取最多 100 条，统一 60 秒 lease，串行发送；若处理超过租约，另一 worker 可领取尚未开始/仍在发送的项目。
- 没有 owner/fencing token，过期 worker 仍可 mark_sent/mark_failed 覆盖新持有者状态。
- 超时直接重试，没有 ambiguous 状态；发送成功后先 mark_sent 再记回执，两步非原子。
- 429 默认固定 60 秒，没有把真实 retry_after 贯穿回执与队列。

**修复要求：** 独立调度发送，投递前复核用户与渠道策略；按单条/小批量获取可续租任务，状态更新校验租约拥有者；网络结果不确定要单独建模；成功状态与回执本地原子写入。不能仅把 lease 调大就宣布并发重复风险消除。

### RV09 · P1 · R：新游标无法正确解析 ISO 时间，翻页直接丢数据

**位置：** `trace/api/routers/events.py:126`；`trace/db/repositories.py:385`。

API 生成 `ISO时间:event_id`，仓储用 `cursor.split(':',1)`。ISO 时间自身含冒号，得到的 c_ts 只有“日期+小时”，余下的时间被当 event_id。

本次建立 3 条事件，用 API 原样返回的 cursor 请求第二页：第一页 total=3、has_more=true，**第二页 items=0**。

**修复要求：** 使用版本化的不透明编码，例如 JSON 两字段经 URL-safe base64 编码，并严格验证字段/时区；对 ID 与时间分别排序。total/has_more 的语义要在 cursor 模式固定；多页期间事件更新也不能仅靠 last_updated_at 上界冒充真正历史快照。

**验收：** API 生成→API 消费至少三页 round-trip；同时间不同 ID、跨时区、恶意/截断 cursor、翻页期间新增和修订；结果不重复不遗漏，或明确约定更新事件如何另行呈现。

## 9. 我的产品判断

这一轮最值得警惕的不是某个漏 import，而是“增加了一个表、函数或测试”被等同于“用户任务已经完成”。研究工作台有 API 但没有客户端路径；新证据匹配有函数但没有事件触发；恢复检查有外键结果却不影响 PASS；安全会话在真正生产模式下没有客户端能用。它们都指向同一个问题：验收没有沿用户和数据的完整路径执行。

下一轮应减少横向铺功能，挑一个完整故事收口：一个用户在生产配置下登录，关注一家公司，收到有证据的事件；随后官方更正到来，系统保留历史、正确修订、按用户偏好通知；中途重启也不丢任务；用户保存的私有假设不被公开，几天后新证据进入复核。

这个故事真正跑通，并经真实用户反复使用，才是 Trace 从工程原型走向可信产品的证据。当前工作值得保留，但验收结论必须比实现文案更严格。
