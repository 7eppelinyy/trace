## 1. 我的判断：值得继续，但应先修复“可信”这一层

Trace 已有一条比普通资讯聚合工具更有价值的链路：采集原始来源、组织事件与修订、通过产业关系识别影响、评分、按订阅提醒、保留投递回执，再尝试用后续行情检验判断。官方来源注册、首次同步保护、增量游标、成本账本和测试体系，都是应该保留的资产。

但是，当前版本还不适合直接作为可信投研产品向普通用户开放。最严重的缺陷不是页面不够漂亮，而是某些页面会把没有依据的数据和结论展示成已经核实的事实；另外，事件处理中断后可能静默漏掉后续分析，身份边界也没有成立。它们会让用户在最需要可靠信息的时候作出错误理解。

我的建议是把产品定位收敛为：

**Trace 是跨市场产业事件的证据与跟踪工作台。它帮助用户理解什么发生了变化、为什么与自己关注的公司有关、结论依赖哪些假设，以及下一步应该验证什么。**

这一定义决定四个优先级：

1. 每个重要事实与数字都有可追溯的来源；不知道就显示不知道。
2. 用户关注的是事件的新增变化，而不是同一新闻的十次转述。
3. 产业链推断必须展示条件、证据与失效条件，不能靠流畅措辞制造确定性。
4. 系统需要可靠地完成跟踪、提醒和纠错，形成长期研究记忆。

我不建议现阶段继续扩充“全市场、全行业、机构级、四级图谱、深度推演”等承诺。先在半导体、存储、AI 基础设施这一小范围内做出可验证的研究价值，再用相同方法扩张。范围可以小，信任标准不能低。

### 1.1 当前成熟度

| 维度 | 审阅判断 | 原因 |
|---|---|---|
| 后端事件流水线 | 有基础的工程原型 | 去重、修订、评分、投递齐全，但持久化任务恢复存在断点 |
| 证据可信度 | 后端有约束，端到端不成立 | 前端伪行情、统一核验标签、模板传导结论绕开后端约束 |
| 小程序 | 可交互原型 | 页面与 API 已连接；多处操作只改变本地状态，异常仍会显示案例 |
| 用户体系 | 开发期隔离方案 | 客户端任意声明用户 ID，没有认证；用户 ID 还与 Telegram chat ID 混用 |
| 运维 | 有历史部署证据 | 有 systemd、备份、健康记录；不等于当前 API/小程序部署已验收 |

| 可收费性 | 尚未验证 | 缺少真实用户的研究效率、提醒有效性与持续使用证据 |

### 1.2 必须保留的现有优点

- 保留 RawItem → Event → EventRevision → EventImpact 的领域分层，不重写成一个聊天接口。
- 保留官方来源注册、来源权威等级和原文链接，补上“来源身份不等于结论正确”的表达。
- 保留首次同步保护与修订白名单，避免历史回填打扰用户。
- 保留生产环境禁止静默伪造的原则，并将其扩展到 API、小程序、缓存和问答。
- 保留成本持久化、交易时段门禁、回测账本，但修正并发、时间与统计口径。
- 保留 SQLite 作为早期部署选项。首先解决状态机、事务和运行责任划分，不为了架构外观立即上多套基础设施。

## 3. 发布阻断问题与具体修复方向

### F01 · P0 · R：真实事件详情混入虚构行情、评分和案例

**位置：** `miniprogram/pages/detail/detail.js:33,54,65,76,103`；`miniprogram/utils/mock.js` 的 `getMockDetailById()`；详情 WXML。

问答图谱的报价被写死为 `1.25%`；真实事件的影响方向被转换成 `±1.5%`；缺失评分变成 `7.0`；真实事件加载失败会显示另一条内置新闻。这不是显示精度问题，而是数据来源发生了替换。自选页面还根据正负展示两条固定 SVG 曲线，容易被理解成真实价格走势。

**修复：** 生产数据转换层只能映射已存在的事实字段，禁止生成价格、收益、评分、来源、确认状态；demo 数据用单独入口、独立包配置和持续“演示数据”标记。真实请求失败不得进入 demo。没有价格历史就不显示迷你走势图。

**验收：** 对 null、0、缺字段、404、503、断网逐一验证；0 是合法数值，null 是未知；失败前后 event_id 不变；正式包不包含可自动触发的 demo 回退路径。见 T01。

### F02 · P0 · R：用户 ID 被当作认证凭据

**位置：** `trace/api/deps.py:20`；`trace/api/routers/watchlist.py`；`miniprogram/utils/api.js` 的 `getUserId()`。

任意请求可通过 header/query 声明身份，不带身份则进入默认用户。UUID 或随机字符串只能减少碰撞，不能证明请求者拥有该账户。跨用户测试目前验证的是两个字符串对应不同数据，没有验证字符串不可冒用。

**修复：** 登录凭据在服务端验证后映射内部 user_id；受保护接口不接受客户端指定所属用户；缺失、过期、无效凭据一律拒绝。访客若有必要，也由服务端发放有期限、可撤销的凭据。旧 `dev_*` 账户不得仅凭旧 ID 自动认领。

**验收：** A 凭据加 B header/query 不能读取或修改 B；匿名操作不落用户数据；删除、重置、日报、问答历史和未来分享接口全部纳入授权测试。CORS 不是身份认证。授权设计参考 [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。见 T02。

### F03 · P0 · R：采集成功不等于事件处理可恢复

**位置：** `trace/pipeline.py:232,240,297,313`；`trace/event_engine/engine.py:135,154`；`trace/db/health.py` 的 HumanReviewRepo。

`pending` 只在内存中保存，游标在 Stage B 前提交。Stage B STOP、进程退出或部分事件处理失败后，下轮采集可能没有新条目，无法重建待分析任务。Stage A 校验失败时，仅写一个指向尚未落库 raw_item_id 的检查记录，随后仍推进游标。另有 RawItem 已写入、Event 尚未创建之间的崩溃窗口：重启会把 RawItem 当重复跳过。

**修复：** 先持久化原始输入与处理任务，再消费任务；用“原始内容已存在”和“对应阶段已完成”两个状态，不能只靠去重决定是否继续处理。网络/LLM 调用放在数据库事务外，阶段结果、任务完成与下一阶段入队在短事务内原子提交。

**验收：** 在 raw 落库后、Stage A 后、事件提交后、Stage B 中、impact 提交后分别强制终止；重启均能继续，且不会重复生成业务实体。人审必须看到原始输入并可重试。见 T03。

### F04 · P0 · R/S：预算并发检查非原子，交互问答可耗尽后台预算

**位置：** `trace/ai/llm_client.py:281,284,341,344`；`trace/ai/budget.py:90`；`trace/app.py`。

新增 `try_consume()` 没有接入真实调用路径；`complete_json/complete_text` 仍先 check 后 consume。两个并发请求能同时通过检查。AskEngine 与分析流水线共享 LLM 对象/预算，没有按用户或用途隔离。恶意流量或正常问答增长可能挤占事件预警分析。

**修复：** 两条调用路径统一使用数据库原子预约；限制用户、IP 和全局并发；划分后台最低保留预算与交互预算；记录输入/输出 token、请求尝试和成本估算版本。仅限制调用次数仍不足以约束长上下文成本。

`try_consume()` 当前也使用默认 DEFERRED 事务先读后写，未来接入时必须处理并发升级失败，而不能假定函数名代表正确性。SQLite 官方文档说明默认延迟事务在读转写时可能返回 SQLITE_BUSY，见 [SQLite transaction](https://www.sqlite.org/lang_transaction.html)。见 T04。

### F05 · P0 · S：回答与图谱的结论强度超过提供给模型的证据

**位置：** `trace/alerts/ask.py:180—221,235—256,308`；`trace/ai/guardrails.py`；`miniprogram/pages/ask/ask.js`。

模型上下文主要包含事件标题、方向、分数，缺少原文片段、发布时间和逐结论引用；没有证据时仍被要求进行财务量化推演，成功返回的状态是 `ok`。图谱由固定四级模板另行生成，并非模型答案或证据关系的忠实映射；没有拓扑时仍填入订单、二供、封测和估值重构等判断。来源数量被解释成“交叉核验”，但多个转载源不代表多个独立证据。空答案前端还会显示“未见突发异动”。

**修复：** 建立事实、推断、情景假设三种输出；默认只有相关证据充足才回答事实性问题。缺数据时明确说明缺什么，并提供可执行的核验步骤。用户主动选择情景推演后，必须列出假设且禁止混入事实流。每个结论引用证据 ID，证据 ID 合法只是最低要求，还要检查内容是否支持结论。

**验收：** 无证据、矛盾证据、仅 filing 元数据、过期证据、历史被伪造、同源转载等金标用例全部覆盖。图谱允许 0/1/2 条真实路径，不得凑满四级。见 T05、T09。

### F06 · P0 · S/H：失败投递没有独立恢复队列，用户身份与 Telegram 渠道混用

**位置：** `trace/pipeline.py` 的 `_deliver()`；`trace/alerts/engine.py`；`trace/main.py:72,528`。

投递失败只记失败回执，没有独立待投递任务扫描。注释“允许下一轮重试”不等于存在自动重试流程：下轮无新事件时通常不会再进入该事件投递。发送成功、写回执前进程崩溃也存在重复窗口。小程序创建的 `dev_*` 用户加入同一订阅表，而 sender 把 user_id 直接当 Telegram chat_id，bot sender 甚至执行 `int(user_id)`。

**修复：** 内部 user_id 与 channel_binding 分离；只有已验证且启用的渠道可投递；事件版本和投递任务在事务中连接。建立 outbox、租约、重试与 ambiguous 状态。网络超时可能意味着已发送但回执未返回，不得承诺端到端绝对 exactly-once。

**验收：** 失败后没有新新闻也能重试；小程序用户无 Telegram 绑定时不调用 Telegram；成功回执之前崩溃能识别不确定投递并按策略处理。Telegram 请求与回执字段以 [Bot API sendMessage](https://core.telegram.org/bots/api#sendmessage) 为准。见 T06。

### F07 · P0 · S：当前 CI 安装清单与实际依赖脱节

**位置：** `.github/workflows/ci.yml`；`requirements.txt`；`tests/test_api.py`。

CI 手写安装依赖，未包含 FastAPI，而测试模块直接 import FastAPI。当地虚拟环境通过不代表干净 CI 环境通过。requirements 全部是下界，部署与测试也没有锁定一致依赖集合。

**修复：** 建立单一依赖来源和可重复解析的锁文件；拆分 runtime/dev/可选 embedding，但 CI 至少覆盖正式部署使用的组合；新建干净环境安装并收集测试。显式选择 hash fixture，不允许单测下载模型或访问公网行情。

**验收：** Windows/Linux 的干净环境均能完成 import、迁移、pytest；新增前端映射测试；禁止以本地已安装包掩盖缺失依赖。见 T07。

## 5. 产品打磨：让用户完成一次真正有价值的研究闭环

### 5.1 首批用户与核心任务（待验证的产品假设）

首批用户定位为：持续跟踪 5—30 家美股/A 股科技公司的个人研究者和小型研究团队。选择这一群体，是因为现有来源、图谱、种子证券与语言能力已经围绕这一范围积累；不是因为已经证明这一群体愿意付费。

核心任务应写成：“我每天有有限时间，帮我找到关注范围内真正发生的新变化，理解影响路径，并记住接下来要验证的事情。”

建议首个版本只服务三个时刻：

| 使用时刻 | 用户要完成的任务 | Trace 应交付的结果 |
|---|---|---|
| 开盘前/开始研究 | 过去一段时间有什么值得注意 | 3—5 条与关注对象有关的变化，附证据、时间、待确认点 |
| 收到重要更新 | 这条消息是否值得打断我 | 一句新增事实、涉及标的、影响条件、与上一版本差异 |
| 收盘后/每周复盘 | 上次判断后来怎样了 | 新证据、已证伪假设、仍未解决的跟踪问题及可复查历史 |

首页第一优先级不应是大盘指数和“最强 AI”入口。指数只是背景信息，真正应占首屏的是“与你有关的新变化”和“你正在等待验证的问题”。

### 5.2 信息架构与页面规格

#### A. 雷达首页：先回答“为什么我该看”

首屏从上到下：用户关注范围/数据更新时间、重要变化列表、待验证问题提示。大盘指数可折叠或下移，不阻塞事件内容加载。

事件卡片包含：

1. 具体、可验证的事件标题，不拼接夸大的影响结论。
2. 状态标签：传闻、媒体报道、部分确认、官方披露、存在矛盾、已撤回；由后端状态产生。
3. 一句“本次新增了什么”，版本更新时优先展示差异。
4. “与你有关”：自选标的及直接/条件性关联理由。
5. 事件时间与采集时间；日期精度不够时直接写“仅日期可用”。
6. 独立来源数与原始证据数分开，避免转载放大可信度。
7. 按钮：“查看证据”“跟踪此事件”“暂不关注”。

默认按与自选的相关性、信息增量和时效排序；使用可解释的确定性排序 v1，不先训练个性化推荐模型。所有权重配置化并记录版本。用户可切回严格时间序；相关性排序不能让严重负面信息因低点击率被隐藏。

空状态必须分为：确实没有新事件、当前筛选无结果、来源覆盖不足、服务暂不可用、有缓存但已过期。只有第一种可写“暂无新的重要变化”。

#### B. 事件详情：先事实，再影响，最后跟踪

推荐布局：

```text
事件标题 + 状态 + 时间精度 + 当前版本
本次变化：较 v2 新增一份官方公告，金额由 X 修订为 Y

事实卡：一条事实一行，右侧引用 [1] [2]
尚不清楚：未披露量产时点 / 未披露订单金额

与我关注公司的关系
  已证实关系：公司 A → 产品 B       [图谱关系证据]
  条件性影响：如果需求兑现，可能影响公司 C 的某业务
  反证条件：订单延期 / 客户份额不变

下一步验证：下次财报是否上调该业务指引
来源与原文：来源类别、发布时间、抓取时间、证据片段
修订时间线：v1 报道 → v2 部分确认 → v3 更正
```

重要度表示“值得研究的程度”；方向是有条件的分析结论；confidence 是模型输出，未经校准不能写成“90% 胜率”。三者不能合成一个“买入指数”。

详情里的图谱采用节点和有依据的边，默认只展开与当前问题有关的路径。每条边点击后看到关系类型、证据、有效时间与条件；没有数据则显示“尚未建立可验证路径”。不要把固定四段文案叫作四级产业图谱。

#### C. 问答：从开放聊天转为带上下文的研究动作

默认从事件/标的进入，携带 `event_id + event_version` 或证券 ID，而非只拼接标题。建议提供四个动作：

- “解释影响”：已知事实怎样传导，哪些环节仍是假设。
- “反方证据”：有什么信息可能推翻当前判断。
- “核对数字”：数值来自哪里，单位、期间、同比/环比是否一致。
- “下一步验证”：生成一个可跟踪、可判定完成的研究问题。

输出以结论、支持证据、推断条件、缺口和后续观察为结构。普通用户不需要看到供应商名、接口地址或所谓“穿透耗时”；运维诊断放在受控开发入口。模型没拿到资料时应直接回答“现有证据不足以判断”，而不是补一篇通用研报。

多标的比较不能只取句子中第一个股票。无法识别对象时返回消歧候选。对话引用可定位原文，继续追问继承已选上下文；不把客户端提交的 assistant 历史当作已验证事实。

#### D. 自选：从股票清单变成研究覆盖清单

每只证券展示：名称、市场、证券状态、最新报价及其时间、未读事件数、覆盖程度、真实生效的提醒策略。

覆盖程度至少包含：已建立官方来源/仅有媒体来源/图谱未覆盖/仅行情可用。用户能添加一只股票，并不代表系统能监控其所有重要事件。新增不在覆盖范围的标的时明确说明能力边界，并允许提交覆盖需求。

提供行业组合模板作为可选择的起点。不要默认为所有用户永久加入“官方核心池”；首次可选，用户清空后保持为空。

#### E. 设置：每个控制都必须真正生效

仅保留账户、关注范围、提醒时段、渠道绑定、默认时区、涨跌颜色偏好、数据/隐私管理、帮助与版本。

推送显示三个独立状态：用户愿望、服务端策略已保存、平台渠道授权/可用性。授权被拒绝时不能显示“已开启”。缓存清理只删除明确允许删除的缓存键，不删除登录凭据、关注列表或正在编辑的内容。

### 5.3 交互审阅：Before / After

结合项目已有设计规范与 emil-design-eng 的“真实反馈、克制动效、边界状态完整”原则，建议如下。此表来自代码审阅，不是已完成真机视觉验收。

| Before | After | Why |
|---|---|---|
| 每张卡片都强调“官方”“权威核验” | 状态来自证据，来源类别和确认程度分别显示 | 用户能区分来源身份与事实状态 |
| 固定四级传导与统一套话 | 展示当前有依据的路径，空缺保持空缺 | 避免界面完整度掩盖证据不足 |
| 方向映射成 ±1.5% | 方向标签与真实行情两个字段，缺失报价用 `--` | 防止把预测当观测 |
| 自选股票使用两条固定走势曲线 | 有真实时序才绘图，否则只显示数值或占位 | 图表应承载数据，而非装饰可信感 |
| 刷新后固定提示已刷新 14 家 | 显示数据更新时间；只有真实触发采集才说明采集结果 | 客户端重拉列表不等于重新抓取来源 |
| API 错误变成空列表或模板研报 | 保留旧内容并显示过期/错误，提供局部重试 | 不让故障看起来像没有事件 |
| “微信推送已开启”只改变本地状态 | 保存中→成功/失败，失败回滚并保留原因 | 操作反馈对应真实结果 |
| 问答结束才逐行模拟流式 | 真流式或明确的一次性加载；不增加人为等待 | 尊重真实延迟与用户注意力 |
| 分享依赖 globalData.customGraph | 分享指向有权限与版本的持久化对象 | 接收方和重启后获得同一内容 |
| 股票搜索可能被旧响应覆盖 | query 序号/取消旧请求；只采纳最新输入结果 | 输入与结果保持一致 |
| 滑动每次读取设备信息并 setData 整个列表 | 缓存尺寸，只更新活动行；提供菜单删除入口 | 降低触摸延迟，兼顾不熟悉手势的用户 |
| 调试域名切换和服务供应商诊断在普通界面 | 正式版稳定入口；管理员单独诊断 | 用户只处理自己能够解决的问题 |

视觉上建议统一暗色层级、线性图标与等宽数字，避免小程序与 HTML 预览各自维护一套设计。涨跌除了颜色还保留符号，用户可选颜色习惯。文本层级要服务事实/推断/未知的分组，而不是靠低对比度把未知藏起来。

建议按钮反馈 100—160ms，普通抽屉 180—250ms；高频列表刷新不做整屏入场动画。只在支持的运行环境使用对应动画能力，不能把浏览器 CSS/React 示例直接复制到 WXML。验证小屏、系统大字体、长中文标题、键盘遮挡、低端 Android 与 iPhone 安全区；真实数字变化不使用滚轮动画，以免影响快速比较。

### 5.4 真正可能形成差异化的能力

**第一，信息变化检测。** 用户已经知道旧新闻，Trace 应告诉他“哪项证据变了，导致哪项结论需要更新”。这比继续增加新闻源数量更接近收费价值。

**第二，假设跟踪。** 从“可能利好某股票”变成“若客户下季指引上修且供应商份额不降，某路径才成立”；系统在新证据到达时提醒重新评估。初期跟踪条件由用户确认，系统不自行执行交易。

**第三，研究记忆。** 保存当时看到了什么、模型/用户作了什么判断、后来如何变化。历史观点可被修正，但不能被覆盖得仿佛从未错过。

**第四，覆盖透明度。** 明确哪些公司/来源/时间段没有覆盖。一个能展示盲区的雷达，比声称全覆盖的资讯列表更值得长期使用。

先用手工策划和用户访谈验证上述能力。不要在没有反馈前建设大规模 agent 自动研究、自动交易或复杂推荐系统。

## 6. 目标数据契约与实现边界

本节是实现约束，不要求一次建设所有表。T01 可先修正展示；T03/T05/T06 分阶段增加持久化模型；T16 再增加研究跟踪。

### 6.1 数据不变量

1. 任何对外数字都必须来自已知数据源或可复算公式；缺失不能用“看起来合理”的常量补齐。
2. `source_is_official`、`claim_status`、`analysis_confidence`、`quote_quality` 是四个不同概念。
3. `published_at`、`occurred_at`、`fetched_at`、`analysis_created_at`、`delivered_at` 分开；时间精度未知必须存储精度与来源。
4. 任何已展示的分析和提醒都能追溯到 event version、analysis version、证据集合、模型/prompt/图谱/评分版本。
5. 原始输入入库不代表提取/分析成功；每阶段有独立、持久化的完成状态。
6. 没有有效绑定的渠道不会进入投递队列；业务用户 ID 不承担渠道地址功能。
7. 行情显示携带市场时点与延迟性质，不能用 fetch time 冒充 market time。
8. 补算与更正不覆盖曾经发出的预测快照。
9. 生产入口不得自动读取演示数据；测试/演示环境的记录不得混入正式指标。
10. HTTP 200、进程存活、采集正常、数据新鲜、结论可用分别建模。

### 6.2 建议新增/调整的存储实体

| 实体 | 最小字段 | 唯一性/迁移要求 |
|---|---|---|
| `raw_document_version` 或现有 raw_item 扩展 | source_id、source_item_id、canonical_url、content_hash、原始载荷引用、fetched_at、published_at、time_precision | 同一 URL 可以有不同内容版本；确定性去重不得丢更新 |
| `processing_job` | job_id、stage、input_id/version、state、attempts、lease_until、next_retry_at、error_code、created_at | `(stage,input_id,input_version,processor_version)` 唯一；增量恢复可重入 |
| `event_claim` | claim_id、event_id/version、text、kind、status、数量/单位/期间、evidence_ids | kind 为 fact/inference/scenario；事实要求证据支持 |
| `analysis_run` | id、event_version、model/provider、prompt_version、graph_version、score_version、evidence_hash、generated_at、status | 追加保存；“当前结果”用显式引用，不覆写历史 |
| `analysis_impact` | analysis_id、security_id、direction、条件、反证条件、confidence、score_breakdown | 对证券的影响隶属分析版本 |
| `channel_binding` | binding_id、user_id、channel、external_subject、verified_at、enabled、permission_state | Telegram/微信地址与内部 user_id 分离；绑定过程防重放 |
| `alert_outbox` | id、user_id、binding_id、event_version、analysis_id、payload_hash、state、attempts、lease、next_retry_at | 业务幂等键需唯一；正文快照不随后台分析漂移 |
| `notification_preference` | user_id、security_id/全局、threshold、quiet_hours、timezone、channel、revision | 先清楚定义全局与单标的优先级；更新可返回版本冲突 |
| `prediction_snapshot` | analysis_id、security_id、predicted_at、observable_at、direction、horizon_rule、entry_rule、model_version | 预测定义在观察结果之前冻结；后续修订创建新版本 |
| `research_question`（后续） | user_id、event_id、hypothesis、supporting/contradicting evidence、next_check、state | 不把用户私有研究默认公开分享 |

数据库迁移从当前最新编号之后新增，执行前重新检查目录，不能假定下一个编号永远是 0014。保留旧列读取兼容期；旧记录无法补出的信息写 unknown/legacy，不得用当前时间或当前模型伪造历史。

### 6.3 作业与投递状态机

```text
原始采集：fetch -> raw 持久化 + extraction job -> 推进可确认游标

分析作业：pending -> leased -> succeeded
                       |-> retry_wait -> pending
                       |-> blocked_budget -> pending（预算恢复后）
                       |-> needs_review -> pending / rejected
                       |-> dead_letter（超限，保留原始输入与原因）

投递：pending -> sending -> sent
                    |-> retry_wait
                    |-> failed_permanent
                    |-> ambiguous（可能已发送，回执不确定）
```

Stage B job 创建必须与事件版本写入在一个短事务里完成；Stage B 输出、完成状态与待投递任务亦如此。采集游标可以在原始输入及提取任务都可靠持久化后前进，不必等网络分析完成。SQLite 单写者条件下用短事务、明确租约与有限重试；禁止把模型调用、网页抓取、消息发送放在写事务内。

重要细节：不要只修成“下轮重扫没有 impact 的事件”。这无法区分合法的无影响结果、半途失败、某版本分析未完成，也无法恢复已有 impact 但投递丢失的情形。没有 impact 也应有一个成功完成且结果为空的 analysis_run。

### 6.4 API vNext 最小契约

保持当前 `/api/v1` 兼容或显式发布新版本，不让后端和小程序各自猜测响应。最先补充的是身份、质量状态、证据与请求 ID，不是新增大量业务端点。

```json
{
  "event_id": "EVT-example",
  "version": 3,
  "status": "reported",
  "event_time": "2026-09-18T12:00:00Z",
  "time_precision": "minute",
  "data_quality": {"state": "partial", "missing": ["order_value"]},
  "claims": [
    {"claim_id": "C1", "kind": "fact", "text": "示例事实，实际内容来自证据", "evidence_ids": ["R1"]},
    {"claim_id": "C2", "kind": "inference", "text": "示例推断", "assumptions": ["需求兑现"], "evidence_ids": ["R1"]}
  ],
  "quote": {
    "price": null,
    "currency": "USD",
    "change_pct": null,
    "change_basis": "previous_close",
    "market_timestamp": null,
    "fetched_at": null,
    "provider": null,
    "quality": "unavailable"
  },
  "analysis": {"id": null, "status": "pending"},
  "request_id": "req-example"
}
```

上例仅定义结构，不是实际新闻。若 `change_basis=previous_close` 缺失，不得悄悄填入 15m 指标。未知时点不允许 quote quality 为实时。

建议错误码：`AUTH_REQUIRED`、`FORBIDDEN`、`RATE_LIMITED`、`BUDGET_EXHAUSTED`、`UPSTREAM_UNAVAILABLE`、`INSUFFICIENT_EVIDENCE`、`NOT_FOUND`。分别匹配恰当 HTTP 状态；合法的“证据不足”研究响应可为 200，但必须是独立领域状态，不能与正常结论混同。客户端收到失败不改写为业务成功，也不把内部路径/原始异常展示给用户。

### 6.5 分析与推断的证据规则

- 事件层面的 evidence_events 列表不够：它可能只证明检索过某事件，不能证明答案中的每个结论。
- 数字引用必须带单位、期间、币种、量级及口径；“上调 20%”与“上调 20 个百分点”分开验证。
- 同源转载归为一个来源簇；官方披露可以确认披露内容，不能自动确认股价方向。
- 原文中的指令视为内容，不授予模型新权限；引用限定在提供的证据集合内，异常结果进入检查队列。
- 结论冲突允许并列展示，不为维持统一方向删除反证。
- confidence 若未经过校准，只标“模型置信度，未校准”；不将 0.9 映射成 90% 获利概率。
- 图谱边需有来源、valid_from/valid_to、关系类型和维护时间。静态 seed 关系不是永久事实。

6. 建立至少 100 对人工核验样本，包含中英同事件、同公司不同季度、同 URL 更正、转载、官方否认；留独立测试集。

**验收：** 首期固定金标误合并=0；召回至少 90% 作为内测目标，按类别报样本量，不宣称总体生产准确率；同 URL 实质修订不丢；模型切换不可静默混用；旧关系过期不会继续当事实。

**回滚：** 保留旧聚类决策及原始文档，合并可撤销；阈值变化先 shadow 评测，再灰度。

### T10 · P1 · 提醒偏好、日报与渠道状态闭环

**修改入口：** 新增 preferences API、`alerts/engine.py`、`alerts/digest.py`、`api/routers/digest.py`、`pipeline.py` 维护任务、`miniprogram/pages/profile/*`、`watchlist/*`。

**验收：** 刷新、重装恢复、两设备读取一致；取消某标的提醒后后台不再投递；用户拒绝微信授权不能被算开通；跨夏令时/跨日期摘要区间正确；同一日期不同用户范围不串缓存。

### T11 · P1 · 事件查询性能、稳定分页与客户端请求治理

**验收：** 10 万事件基准库分页不漏失指定筛选结果；并发新增期间遵守定义的快照分页语义；数据库查询次数不随一页事件数线性增长；慢行情不阻断事件正文；旧搜索响应不覆盖新 query；连点不双重扣费。

**回滚：** 可恢复原端点路由但保留数据完整性，不能重新悄悄截断结果。

### T12 · P1 · 行情语义、交易日历和跨周末补算

**依赖：** T03 的持久化作业；时间契约先与 T13 定稿。**对应：** F15—F18。**预估：** 3—6 人日。

**修改入口：** `collectors/market_data/*`、`api/routers/market.py`、`api/schemas.py`、`market_time/*`、`pipeline.py:_rescore_market_confirmations`、`db/repositories.py`。

**执行：**

**验收：** 周五盘后→周一、长假、午休、夏令时、早收盘、停牌、过期报价、供应商时间缺失、跨年均有 fixture；日涨跌不可被 15m 替代；旧报价不能参与评分；日历异常时安全降级。

**回滚：** 无可靠行情时保留中性市场确认及显式原因，禁止回滚成用旧报价补评分。

### T13 · P1 · 不可变预测快照与可解释效果评估

| 门槛 | 完成范围 | 允许做什么 | 不通过时怎么处理 |

### 8.3 推荐切片与停止扩张条件

**第一切片：阻断错误承诺。** 先交 T01/T07 和 T02/T04 的最小安全边界；最迟在任何扩大外部访问前完成。暂时关闭坏功能比用假数据填满屏幕更符合产品目标。

**第二切片：一次事件真正走完。** T03 + T06 + T05 的证据约束，用一条伪采集但完全可重放的事件覆盖采集、分析、显示、用户设置、失败恢复、投递和修订。

**第三切片：有限领域连续运行。** T08—T15 围绕半导体/存储样本做两周观察；记录漏报、错并、无效提醒和覆盖盲区。

**第四切片：跟踪价值。** 做 T16；与用户现有阅读工作流比较，观察产品是否让用户减少重复查找、记住待验证问题。

出现以下任一情况，暂停新来源、新市场、新动效与商业扩张：伪数字再出现；对象授权失败；积压持续增长；指标无法解释分母；高价值事件漏分析；用户已关闭提醒仍被通知；无法恢复备份。停止的是扩张，不是修复工作。

### 8.4 明确延后

- 自动交易、个性化买卖建议、目标价排行榜。
- 全市场无限证券覆盖、全行业图谱、任意问题的长篇研报。
- 为低规模使用引入微服务集群、Kafka、多个向量数据库。
- 未有真实价格数据的装饰图表、固定四级图谱、以动效掩盖模型等待。
- 在没有团队用户证据前做复杂工作区/RBAC 套餐；但底层用户隔离必须立即正确。

## 9. 指标：衡量用户是否少错过重要变化，而不是模型写了多少字

以下数值都是**建议的内测目标**，不是当前测量结果、行业标准或保证。上线前先收一周基线，依据来源频率和运行成本修订并版本化。

### 9.1 产品与研究价值

| 指标 | 定义与分母 | 初期用途/目标 |
|---|---|---|
| 周有效研究用户 | 一周内完成至少一次“看证据 + 保存跟踪/标记结论”的去重用户 | 北极星候选；不把单次打开算研究价值 |
| 首次价值时间 | 从首次进入到打开一条与关注证券相关、可查看证据的事件 | 任务观察中位数 ≤3 分钟；需测试无新闻用户 |
| 有用提醒比例 | 用户已反馈“有用”的提醒 / 已获得反馈的提醒 | 首期目标 ≥70%；同时公开反馈覆盖率，不能把未反馈算有用 |
| 重复打扰率 | 用户认为无新增信息的重复提醒 / 已评估提醒 | <2%，按事件簇计算并人工抽检 |
| 研究问题闭环率 | 到期研究问题中已复核/明确延期/关闭的数量占比 | 观察工作流是否真正持续，暂不设营销目标 |
| 7/28 日研究留存 | 激活 cohort 在相应窗口再次完成研究动作的用户比例 | 小样本展示人数与原因，不只给百分比 |

### 9.2 内容质量

- **无来源事实率：** 抽检中的事实性结论缺少支持证据的比例；数字、来源状态与时间错误为零容忍发布缺陷。
- **引用支持率：** 不仅 ID 存在，还要人工判断片段是否支持该句结论。金标目标 ≥95%，高影响数字必须全部通过。
- **覆盖召回率：** 人工整理的约定覆盖域内重大事件中，系统在目标时限发现的比例。必须维护系统之外的抽样来源，不能用自己采到的数据当分母。
- **去重质量：** 误合并、漏合并分开；避免为了看上去“少重复”把不同季度财报合并。
- **状态正确率：** reported/confirmed/contradicted/retracted 是否与证据一致；来源官方不代表所有推论 confirmed。
- **模型安全评测：** 同时统计越权/注入成功率与正常金融问题误拒率；“拦住关键词”不等于整体安全。

### 9.3 可靠性与延迟

| 指标 | 定义 | 建议初期目标 |
|---|---|---|
| API 可用性 | 经外部探测的关键只读接口成功率，排除明确拒绝访问 | 连续 14 天 ≥99.5%，维护窗口单独记录 |
| 事件读取延迟 | 服务器收到请求到事件正文响应，不含行情/模型 | 10 万事件、约定硬件、20 并发下 P95 <500ms |
| 采集至可用延迟 | raw fetched_at → 经验证事件可查询 | 常规负载 P95 <2 分钟；与发布到采集延迟分开 |
| 发布至发现延迟 | published_at → fetched_at | 精确时间源目标 ≤2 个轮询周期+60s；日期级来源不计算伪精度 |
| 已持久化任务丢失数 |故障注入后最终既未成功也无明确失败状态的任务 | 0 |
| 队列老化 | oldest_pending_age / backlog_size | 正常状态不能长期超过 2 个处理周期；预算暂停单列 |
| 已确认投递重复 | 同业务幂等键多条已确认回执 | 本地并发测试=0；网络 ambiguous 单列，不宣称绝对零重复 |
| 数据恢复 | 隔离备份恢复实测 | 内测 RPO ≤24h、RTO ≤2h；付费前再按价值决定是否提升 |

### 9.4 成本与可持续性

按“成功分析一个事件版本”“成功回答一个证据问题”“一个周活跃研究用户”分摊成本。至少计入采集/模型输入输出/重试/行情/存储/通知，区分增量成本与固定成本。

每日 3000 次上限不是财务预算。模型不同、上下文不同、SDK 重试不同，单次成本差异很大。先记录 provider/model/token/attempt/用途，费用估算记录价目版本；供应商账单核对后再决定定价。限额不应随意牺牲后台关键事件能力。

## 13. 最后的产品取舍

Trace 最有潜力的地方，是它已经把“事件”“证据”“修订”“产业关系”“提醒”这些长期有价值的概念连接起来。下一步需要让这些概念真正成为用户能理解、能检查、能依赖的产品。

我心目中值得长期使用的 Trace，会在重要时刻给用户这样一种体验：一条提醒讲清发生了什么变化；点开后能看到原文和不确定性；几天后系统记得当时的判断，并在新证据到来时主动指出哪里需要修改。即使模型错了，用户也能知道它为什么错、错误影响了哪些结论，以及系统已经怎样纠正。

做到这一点，比输出更长的分析、显示更多分数或把图谱画得更复杂都更难，也更有价值。产品的竞争力会来自可信的记录、及时的变化和完整的研究闭环。
